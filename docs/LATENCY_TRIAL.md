# GELLO 遥操作延迟候选版

状态：2026-10-31，已完成离线验证，未启动真机。`main` / `baseline-20261031` 保留上传时原版。候选分支 `codex/teleop-latency-trial` 必须经使用者真机测试后才考虑合入。

## 定位依据

七轴在同一次 1 kHz 回调中更新，没有“抬手完成才转腕”的串行命令。以下因素会造成不同轴看起来先后到位：

1. 原来目标更新与采集、HDF5 append/flush 在同一线程。配置为 15 Hz，理想每 66.7 ms 才有一个新目标。只读分析最近一条 1041 帧实际记录，帧/命令更新间隔中位数 101.6 ms，P95 160.0 ms；发送到 ACK 中位数只有 0.66 ms。真实记录不能单独归因所有耗时，但代码路径和独立写盘负载对照支持先移开同步写盘。
2. 参考速度上限为每轴 0.2 rad/s。单轴目标领先 0.3 rad 时，仅参考追赶就至少需要 1.5 秒；提高发送频率不能消除这项限制。本候选暂不提高速度。
3. 原 torque PD 为 `Kp*(q_ref-q) - Kd*dq`，阻尼始终针对零速度。J1–J5 的 Kp=120，J6=150，J7=60，Kd 都为20。忽略惯性/外力、假定恒速跟踪时，平衡误差近似 `Kd*v/Kp`；在 0.2 rad/s 下 J7 约 0.067 rad，而 J1 约 0.033 rad。这是控制律解释，不是实测延迟估计，也不证明全部旋转迟滞由它引起。

## 三组配置

| 配置 | 控制目标更新 | 数据记录 | 速度前馈 |
|---|---:|---:|---:|
| baseline | 15 Hz，同步写盘 | 15 Hz | 0 |
| fast | 100 Hz，后台写盘 | 15 Hz | 0 |
| feedforward | 100 Hz，后台写盘 | 15 Hz | 0.5 |

`baseline` 是独立副本里的对照配置；精确原源码仍在 Git 标签中。

`fast` 每次 tick 同时读取、发送全部七轴目标；只在记录时点获取图像快照。后台队列最多8帧，满队列、写盘异常、过期 GELLO 缓存都报错并走既有停止流程，不静默丢帧。正常保存时会继续发送 hold 心跳。错过记录时点不会补发突发帧或伪造时间戳。快照仍含实际命令 sequence/ACK，训练动作仍由相邻实测状态离线生成。

`feedforward` 在原 PD 上加 `Kd * 0.5 * v_ref_filtered`。参考来自现有速度受限轨迹，不差分 USB 输入；补偿参考速度按原加速度参数渐变。它应用于全部七轴，用于单独检验运动中阻尼造成的滞后。保持、停止、回位时补偿归零。速度、Kp/Kd、力矩夹限、碰撞阈值、libfranka 限幅及看门狗没有提高或关闭。此项可能改变起停、反向及接触时手感，必须作为第二阶段独立比较，尚未实机验收。

原 torque 分支本来就没有 position backend 的跟踪误差急停，也不是 jerk 限制的运动轨迹；本改动不把它描述成具备这些保证。

## 离线验证

全部在 `/home/heinrich/robolab-control-system` 中运行，原环境仅作只读 Python 依赖来源。没有访问真实 FCI、相机或串口，也没有修改服务/调度配置。

- 真实 libfranka + Robotiq SDK 分支构建成功，C++ 测试2项通过。
- Python 测试91项通过，包括快速控制/15 Hz记录、暂停优先、不补发记录、后台错误/背压、保存期间 hold 心跳、过期 GELLO 缓存。
- 回归测试先在原逻辑下失败：10次控制调用写了10帧而不是2帧；移动参考匹配时仍有零速阻尼。证据在 `docs/latency/*red.log`。
- 6秒 CPU/mock 对照：使用已有真实图片作为写盘纹理负载，输出始终标记 mock，不是真机 rollout，也不用于训练。

| 指标 | baseline | fast |
|---|---:|---:|
| 命令数 / 记录帧数 | 90 / 90 | 600 / 90 |
| 命令间隔 P50 | 66.68 ms | 10.06 ms |
| 命令间隔 P95 | 67.40 ms | 11.01 ms |
| 控制 tick 耗时 P50 | 44.91 ms | 1.33 ms |
| 控制 tick 耗时 P95 | 50.47 ms | 3.25 ms |

双方 HDF5 完整性与时间戳检查通过。100 Hz 与15 Hz的时点量化使 fast 记录间隔通常为60/70 ms；6秒总帧数仍为90，并保留真实时间。上述数值不含真实 USB/相机负载与机械响应，不能宣称真机端到端延迟已降到10 ms。线程方案也不提供硬实时保证；存储持续跟不上时会明确停止。

## 仅测试遥操作、不接相机

Kinect/D405 未连接时，可明确选择不录数据的入口。程序不构造相机对象、不创建 HDF5 writer，也不拿合成图像代替真实图像：

```sh
cd /home/heinrich/robolab-control-system
./scripts/try_latency.sh fast --execute --teleop-only
```

仍按 Enter 启动设备、Enter 回位、Enter 开始跟随；再次 Enter 停止并结束本轮，q 退出。不需要成功/失败标注，仅保存诊断事件。此模式适合检查控制手感，不能代表双相机数采负载下的运行效果。此次修复后96项 Python 回归测试通过；验证仅使用隔离测试，没有代替操作者启动真机。

启动前的 `fix_fci_network_priority.py --apply` 已支持重复执行：缺少协调锁时安全创建并设置为 heinrich 所有，已为 FIFO 50 时直接成功返回；被占用的锁、符号链接锁以及未知调度状态仍拒绝操作。这里只修改候选脚本，没有修改系统调度或原代码目录。


每组做相同的小幅空中抬手+转腕动作，分别观察开始跟随、匀速跟随、停止和反向；仅试动请标记 `a`。结果写入本目录的 `reports/latency_trials/<profile>/` 和 `data/latency_trials/<profile>/`，不自动导出到训练集。事件日志保存控制周期分位数和记录队列峰值。对比手感及记录后再决定保留 fast、启用前馈或进一步评估速度限制。
